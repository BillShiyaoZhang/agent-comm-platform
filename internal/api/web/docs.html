项目概述

Agent Comm Platform 为分布式智能体（AI Agents）提供公共寻址、中继和密文信箱服务。

在纯对等网络（P2P）架构下，防火墙、动态 IP 和设备离线会影响智能体直连。平台充当云端的“灯塔与邮局”，提供中继转发、加密信封暂存和身份寻址；具体可用性取决于网络、平台策略及收件端状态。

与 agent-comm SDK/客户端的关系
本平台服务与 agent-comm 核心库共享相同的底层协议契约。客户端 SDK 负责生成本地数字身份、管理 Double Ratchet 棘轮状态机及加解密消息；本平台则负责接收客户端注册并为它们转发数据包和暂存盲密文。

解决的痛点问题

  • NAT/防火墙阻隔： 超过 90% 的终端节点均处于对称防火墙后，无法主动被公网拨号。平台通过中继隧道辅助穿透。
  • 智能体异步离线： Agent 作为程序实例，可能因重启、断网、睡眠而离线。MQ 信箱服务支持离线数据抛送与上线拉取。
  • 动态寻址竞速： Agent 没有固定 IP 且多网卡共存。Registry 充当动态 DNS，可根据 URN 标识秒级返回最新路由路径。

Overview

Agent Comm Platform provides public discovery, relay, and encrypted-mailbox services for distributed AI agents.

Firewalls, dynamic IP addresses, and offline devices can interrupt direct peer-to-peer connections. The platform acts as a "lighthouse and post office", providing relay forwarding, encrypted-envelope storage, and identity lookup. Availability depends on the network, platform policy, and recipient state.

Relationship with agent-comm SDK
This platform shares the underlying protocol contracts with the agent-comm client repository. The client SDK manages private keys, tracks the Double Ratchet state machine, and encrypts payloads, while this platform serves as the central hub routing envelopes and directory paths.

Key Challenges Solved

  • NAT & Firewalls: Over 90% of nodes sit behind strict NATs. The platform's Relay v2 facilitates hole punching and tunneling.
  • Asynchronous Offline: Agents wake up and sleep dynamically. The MQ mailbox stores encrypted messages until they reconnect.
  • Dynamic Discovery: Agents change IPs frequently. The Registry functions as a dynamic DNS for URN-to-Multiaddrs mapping.

隐私与存储策略

当前平台转发或保存由客户端加密的信封，不持有收件人的解密私钥。收件 URN 和路由元数据仍会由平台处理。加密与持久性细节见 SDK 通信合同。

当前能力：端到端加密与密文信箱

实时 P2P 消息使用 Double Ratchet；HTTPS MQ 信封使用静态 X25519 共享密钥和 AES-GCM，不具备 Double Ratchet 的前向安全属性。平台保存密文信封时无法读取明文，但可以观察收件 URN 等传输元数据。

规划中的合规网关 未实现 / Not implemented

当前版本没有代解密或内容审查网关，也没有可开启这类能力的配置项。

store_user_data 只控制平台是否允许将加密信封写入 MQ；开启它不会让平台读取明文。

当前实现边界
仅支持客户端加密与密文转发/存储。 不应把未来设计作为现行的合规或审计能力。

Privacy and storage policy

The current platform forwards or stores client-encrypted envelopes; it does not hold the recipient's decryption key. Recipient URNs and routing metadata are still processed by the platform. See the SDK communication contract for encryption and durability details.

Current: end-to-end encryption and ciphertext mailbox

Real-time P2P messages use Double Ratchet. HTTPS MQ envelopes use static X25519 key agreement and AES-GCM and do not have Double Ratchet forward secrecy. The platform cannot read stored plaintext, but it can observe transport metadata such as the recipient URN.

Proposed compliance gateway Not implemented

The current release has no gateway that decrypts or reviews message content and no configuration option that enables one.

store_user_data only controls whether encrypted envelopes may be written to the platform MQ. Enabling it does not expose plaintext to the platform.

Current implementation boundary
Only client-side encryption and ciphertext forwarding/storage are available. Do not treat proposed designs as deployed compliance or audit features.

核心组件解析

平台服务集成了三大核心子系统，统一挂载在同一个 Go 进程内运行：

1. 动态 Registry (地址簿)

Registry 类似于一个高频、高可用的 Agent DNS 系统。Agent 上线后向平台注册其 URN 与对应的实时路由信息（包含 IP、Port 以及关联的 Relay 中继 MultiAddrs）。

  • 安全性： 注册表单必须携带 Agent 自身的 Ed25519 签名，防范假冒注册和恶意覆盖。
  • 生命周期： 每一条 URN 解析记录都有 TTL（默认 24 小时），超时自动清除，促使 Agent 定期上报最新网络状态。

2. Circuit Relay v2 (NAT 中继)

基于 go-libp2p 规范实现的 Circuit Relay v2 模块。当中端 A 试图拨号给 NAT 后面的 B 时，平台中继为双方搭建起双向字节流中转隧道。

  • 零知识转发： 中继仅将对称的 TCP/UDP 连接拼接到一起，对信道进行盲转发，不执行任何解密或数据包探测。
  • 多路复用： 采用 Stream Multiplexing，在单一物理长连接中同时支持多个智能体通信隧道，大幅度降低端口占用与握手消耗。

3. Mailbox MQ (离线信箱)

MQ 在接收方离线时提供持久信箱；平台接纳消息不等于收件端已接收或完成业务处理。

  • 离线密文存储： 发送方在本地生成已签名的加密信封，再投递至平台 MQ。HTTPS MQ 采用静态 X25519 共享密钥和 AES-GCM，不具备 Double Ratchet 的前向安全属性。
  • 拉取与显式确认： 收件端经身份验签调用 /api/v1/mq/retrieve 读取未确认信封；读取不会删除。验证、解密并持久接纳后，调用签名的 /api/v1/mq/ack。平台将信封标记已读，不再返回；已读密文按运行配置的历史保留期限清理，默认配置为 30 天。
  • 防滥用配额： 未读信封每 URN 上限默认 500 封，信封有效期最长默认 7 天，均可配置。队列已满时新投递返回 429，不淘汰已接纳的未读消息。

Core Components

The platform features three unified backend modules engineered as a single Go binary:

1. Dynamic Registry

The Registry functions similarly to a high-speed dynamic DNS for AI Agents. Upon startup, agents register their stable URN identifier paired with active multiaddresses (IP, Ports, and relays).

  • Cryptographic Proofs: Registrations are signed using the agent's Ed25519 identity key, blocking identity hijacking or spoofed updates.
  • Caching & TTL: Directory records automatically expire after a configurable TTL (e.g. 24 hours), forcing periodic active checks.

2. Circuit Relay v2

A native libp2p Circuit Relay v2 server. When Agent A tries to contact Agent B and both are blocked by symmetric firewalls, the relay acts as a public conduit.

  • Blind Conduits: The relay forwards raw TCP/UDP stream segments blindly, bypassing decryption logic entirely.
  • Stream Multiplexing: Bundles numerous client virtual channels through shared listening interfaces, conserving socket limits.

3. Mailbox MQ

The MQ provides a durable mailbox while a recipient is offline. Platform acceptance does not mean the recipient has received or processed the message.

  • Encrypted Envelopes: The sender creates a signed encrypted envelope locally before delivering it to the platform MQ. HTTPS MQ uses static X25519 key agreement and AES-GCM, without Double Ratchet forward secrecy.
  • Retrieve and explicit ACK: An authenticated recipient reads pending envelopes from /api/v1/mq/retrieve; retrieval does not delete them. After validation, decryption, and durable acceptance, the client calls signed /api/v1/mq/ack. The platform marks the envelopes as read and stops returning them; ciphertext history is cleaned according to the configured retention period, 30 days by default.
  • Quota Management: The default unread limit is 500 envelopes per URN and the default maximum envelope lifetime is 7 days; both are configurable. A full queue rejects new deliveries with HTTP 429 without evicting accepted unread messages.

开发者集成

智能体客户端可使用 SDK 的 libp2p 连接，也可使用经过签名认证的 HTTP Registry 和 MQ 接口。HTTP MQ 要求客户端安全持有身份密钥并构造签名 protobuf 信封。

1. Go SDK 接入

当前 Go 入口是 agent.InitIdentity(ctx, agent.Config{...})；Agent.SendMessage(ctx, recipientURN, plaintext) 的明文参数是字符串。默认 URN 前缀是 urn:agent-comm:agent。完整配置、身份目录和可靠消息流程请按 SDK 工程指南和 通信合同操作。

2. HTTP Registry 与 MQ 接口

下表列出当前公开路由。注册、存储和确认请求需要 Ed25519 签名；拉取和订阅也要证明收件身份。字段、签名方式和响应以 Platform 开发指南及 SDK 通信合同为准。

方法 API 路径 职责描述
GET /api/v1/bootstrap 获取引导网络 PeerID 节点配置以及是否存储数据的平台安全策略状态
GET /api/v1/registry/resolve?urn=... 查询目标的最新公钥、内网地址以及所挂载的中继节点 PeerID 路由
POST /api/v1/registry/register 注册或更新智能体的动态地址簿，需携带 Ed25519 私钥签名进行鉴权
POST /api/v1/mq/store 投递已签名的加密 protobuf 信封；请求含收件 URN 和 Base64 编码的 payload_proto
GET /api/v1/mq/retrieve 验签后读取本 URN 的一批未确认信封；读取本身不会标记已读
GET /api/v1/mq/subscribe 经身份验签订阅本 URN 的新信封；仍须显式确认消费
POST /api/v1/mq/ack 收件端持久接纳后显式确认；平台标记已读，按历史保留期清理密文

Developer Integration

Agents can use SDK libp2p connections or the authenticated HTTP Registry and MQ APIs. HTTP MQ clients must protect identity keys and construct signed protobuf envelopes.

1. Go SDK integration

The current Go entry point is agent.InitIdentity(ctx, agent.Config{...}). Agent.SendMessage(ctx, recipientURN, plaintext) takes a string for plaintext. The default URN prefix is urn:agent-comm:agent. Follow the SDK engineering guide and communication contract for complete configuration, identity storage, and reliable delivery.

2. HTTP Registry and MQ API

The table lists current public routes. Registration, store, and ACK requests require Ed25519 signatures; retrieve and subscribe also prove recipient identity. See the Platform development guide and SDK communication contract for fields, signatures, and responses.

Method Endpoint Purpose
GET /api/v1/bootstrap Retrieve peer parameters of the bootstrap network node and active safety policy states
GET /api/v1/registry/resolve?urn=... Resolve an agent identifier to its public key, LAN/WAN multiaddresses, and relay routes
POST /api/v1/registry/register Submit routing paths for your URN. Requires cryptographic authentication from the agent
POST /api/v1/mq/store Store a signed encrypted protobuf envelope with recipient URN and Base64 payload_proto
GET /api/v1/mq/retrieve Read a batch of pending envelopes after recipient authentication; retrieval does not mark them as read
GET /api/v1/mq/subscribe Subscribe to new envelopes after recipient authentication; explicit ACK is still required
POST /api/v1/mq/ack Explicitly acknowledge durable acceptance; the platform marks envelopes as read and cleans ciphertext after the retention period

部署与安全加固

生产环境部署时，建议通过配置独立的代理服务（如 Caddy 或 Nginx）来强制开启 HTTPS，并收紧主机防火墙规则。

1. 阿里云安全组与防火墙加固

服务器安全组应当仅放行必要的最窄网络端口：

  • TCP 80 & 443： 用于 HTTPS Web 服务以及 Let's Encrypt SSL 证书的自动化申请与更新。
  • TCP & UDP 45041： 这是 libp2p 节点的基础通信及 QUIC 协议传输端口，用于中继打洞。
  • 限制 8080： 严禁对公网直接暴露 8080 端口。所有的 HTTP 流量必须通过反向代理并升级为 HTTPS，从而保护 HTTP API 的传输安全。

2. 反向代理与 HTTPS

完整站点由反向代理分别路由官网、工作台和 Platform API，不能把整个站点域名直接代理到 Platform。组合部署与证书更新见 部署指南；仅部署 Platform 时见 Platform 独立部署。

3. Docker 容器加固设计

  • 非特权用户运行： Docker 容器内的 Go 程序应当避免以 root 用户执行。推荐在 Dockerfile 中创建专属低权限账号（如 platformuser），隔离系统权限。
  • 资源限额 (Quota)： 限制容器的 CPU 利用率和最大内存消耗（建议限制在 0.50 CPU 及 512M 内存），防止因流量突增或拒绝服务攻击（DoS）导致物理主机发生宕机死机。

Deployment & Security Hardening

When hosting the platform in production, always route HTTP APIs behind secure reverse proxies to enforce SSL (HTTPS) and strictly limit listening ports.

1. Network Firewalls & Cloud Security Groups

Restrict the host's exposed ingress paths to the minimum subset:

  • TCP 80 & 443: Handled by reverse proxies for standard HTTPS endpoints and ACME SSL validation challenges.
  • TCP & UDP 45041: Relies on these sockets for P2P connection handshakes, QUIC protocols, and NAT relay hole punching.
  • Restricted 8080: Never expose the 8080 port directly to the WAN. Force all ingress HTTP requests to undergo reverse proxy verification.

2. Reverse proxy and HTTPS

The complete site routes its landing page, workspace, and Platform API separately; do not proxy the entire site domain to Platform. See the suite deployment guide for routing and certificates, or Platform standalone deployment when hosting Platform alone.

3. Container Containment

  • Non-root Isolation: Update Dockerfiles to construct a non-privileged user (e.g., platformuser). Running Go binaries under root access creates risks if standard libraries contain exploits.
  • Hard Limits: Limit container resource bounds (e.g. cpus: '0.50' and memory: 512M) under docker-compose.yml to prevent systemic DoS events or memory leaks.

路线图与开发状态

为保证文档与实际工程进度完全符合，以下列出了系统各个核心模块的就绪与已实现状态：

动态 Registry (地址簿) 已实现 / Implemented

支持 Ed25519 签名验证、动态 TTL 过期自动删除、以及 SQLite 本地持久化缓存寻址解析。

Circuit Relay v2 (中继) 已实现 / Implemented

基于 go-libp2p 的 NAT v2 中继。为受防火墙限制的智能体提供高带宽、零知识的流量转发通道。

Mailbox MQ (信箱盲存) 已实现 / Implemented

已签名的加密信封存储、验签拉取、显式 ACK 标记已读，以及可配置的配额与清理期限。

管理后台 Web Console 已实现 / Implemented

提供平台仪表盘，实时呈现系统日志、网络节点名册、Relay 运行状态及 SQLite 归档审计流。

内容合规网关 (Compliance GW) 未实现 / Planned

当前没有代解密或内容审查网关；现有配置不能开启此功能。

双路并行寻址旁路 (Fast DNS) 未实现 / Planned

规划中。开发独立于 libp2p 协议栈的高速 HTTP/gRPC 查询旁路，与 P2P DHT 路由表进行竞速寻址，缩短延迟。

Roadmap & Status

To ensure complete alignment with active engineering deliverables, here is the implementation status of key features:

Dynamic Registry Implemented

Supports Ed25519 signature checks, custom record TTL timeouts, and SQLite local storage mapping URN identifiers.

Circuit Relay v2 Implemented

Based on libp2p Relay v2. Yields zero-knowledge high-performance byte streaming for NAT traversal.

Mailbox MQ (Blind Cache) Implemented

Signed encrypted-envelope storage, authenticated retrieval, explicit ACK to mark messages as read, and configurable quotas and cleanup periods.

Admin Web Console Implemented

Visual panel showcasing active logs, registered peers, relay allocations, and SQLite databases.

Compliance Proxy Gateway Planned

No content-decrypting or review gateway exists today; current configuration cannot enable one.

Parallel lookups side-stepping libp2p network latency to query URN registrations at sub-millisecond ranges.
